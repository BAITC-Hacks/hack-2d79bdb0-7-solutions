# Контекст для следующего участника и ИИ

## Актуальное дополнение: asanali/remake, 23 сентября 2026

По запросу Асанали интерфейс упрощён до рекомендованных заказов: артикул, поставщик, количество, обоснование, срочность. Убраны карточки, сообщения качества, панель методологии, утверждение в UI и переключатель всплесков. Очистка всплесков в HTTP-расчёте включена постоянно. Экспорт текущего фильтра выдаёт рекомендации, не утверждённые заказы; прежние API утверждения и их проверки сохранены.

Добавлен OpenAI Responses API для кратких обоснований текущей страницы. Ключ из серверной переменной окружения или игнорируемого .env, модель OPENAI_MODEL (по умолчанию gpt-4o-mini). Внешнему API передаются только индекс и булевы признаки, без названий, поставщиков, кодов, количеств и Excel. Количество, срочность и формула вычисляются прежним движком. При ошибке API доступны расчётные обоснования. Реальный вызов проверен на синтетической позиции: status=ready. 35 тестов проходят, JavaScript syntax check проходит.

Реальные 12 Excel уже предоставлены Асанали и локально импортированы: 3 908 товаров, 416 положительных рекомендаций. В новом дашборде срочные считаются только среди рекомендаций: 232 позиции; прежние 315 включали также товары без положительного заказа. Подробные отчёты сверки находятся в игнорируемой data/. Нижеследующие разделы описывают предыдущую версию; актуальный сценарий — в README и DEMO.

Состояние передачи: 23 сентября 2026. Этот файл описывает реализованную исходную версию, а не обещанный будущий продукт.

## Команда и задача

7-Solutions: Мадияр и Асанали. Хакатон HackAlem AI, направление «Логистика». Владелец кейса — ТОО «Электрокомплект». Официальный сайт: https://hackalem.ai. Общий репозиторий: https://github.com/BAITC-Hacks/hack-2d79bdb0-7-solutions.

Закупщик вручную объединяет Excel и редко рассчитывает заказ. Разовые проектные продажи завышают регулярную потребность, отсутствие товара скрывает спрос. Цель — рекомендуемый заказ по поставщикам, с понятным обоснованием, корректировкой менеджером и экспортом.

Пять обязательных требований кейса: использовать все переданные источники для расчёта; учитывать сезонность и устойчивый рост; компенсировать спрос при stockout; исключать разовые крупные заказы, в том числе клиентские; группировать заказы по поставщику с объяснениями. Подтверждение сотрудником обязательно. README должен объяснять метод и запуск.

## Быстрый старт для Асанали

1. Клонировать общий репозиторий. Если он уже есть, проверить незакоммиченные изменения и обновить main без их потери.
2. Прочитать `AGENTS.md`, этот файл, `README.md`, `TASKS.md`, `CONTRIBUTING.md`.
3. Создать Python-окружение, установить `requirements.txt`, запустить тесты.
4. Запустить `python server.py`, открыть http://127.0.0.1:8765 и выбрать «Демо-сценарии».
5. Для реальных данных получить у команды два исходных ZIP и загрузить их в интерфейсе. Реальные выгрузки и `data/dataset.json` не входят в исходники Git.
6. Выбрать одну свободную задачу, создать ветку `asanali/<task>`, записать область изменений в `TASKS.md`.

## Карта кода и API

| Файл | Ответственность |
|---|---|
| `engine.py` | `detect_outliers`, `calculate_item`, `calculate`; чистые вычисления без HTTP |
| `importer.py` | Чтение Excel из ZIP, объединение справочников, проверка нормализованного JSON |
| `server.py` | Локальный HTTP-сервер, чтение набора, хранение расчётов в памяти, сохранение заказов |
| `demo.py` | Изолированные синтетические сценарии |
| `static/index.html`, `style.css`, `app.js` | Интерфейс, фильтры, состояния, диалоги и запросы API |
| `tests/test_engine.py`, `tests/test_api.py` | Функциональные инварианты и полный цикл API |

`GET /api/status`: доступность данных и токен локальной сессии. `POST /api/calculate`: `{demo, options}` → строки, сводка, ID расчёта. `POST /api/import`: бинарный ZIP либо JSON с заголовком X-Filename. `POST /api/approve`: ID расчёта, ответственный, отображение ID позиции в количество. `GET /api/export?id=...`: CSV утверждения. `GET /api/template`: синтетический пример JSON. POST требует X-App-Token, выданный статусом. Этот механизм не является полноценной пользовательской аутентификацией.

## Реальные данные и важные открытия

На компьютере Мадияра импортированы 12 Excel из `Systeme electric.zip` и `IEK.zip`. Объединение дало 3 908 позиций: 724 Systeme Electric и 3 184 IEK; 248 467 положительных строк расходных накладных.

Изначально были просмотрены отрицательные строки в начале выгрузок, но полная проверка показала, что основные продажи положительные. Импорт исправлен; не возвращать раннее предположение о знаках.

У Systeme есть 497 подтверждённых свободных остатков из отчёта на 22.09.2026. У остальных записей остатки месячные либо неизвестны. В исходниках нет ID клиента, точных ежедневных stockout и полного справочника договорных сроков. Некоторые позиции имеют конфликт кратности, разные единицы учёта и закупки, отсутствие истории или категории. Отсутствующие данные честно отмечены и при необходимости блокируют утверждение.

На стандартных параметрах проверенная версия дала 416 предварительных позиций к заказу, 315 рисков дефицита и 83 позиции к заказу без блокировок. Эти показатели зависят от версии алгоритма, параметров и исходных файлов; это не доказательство точности и не измеренная экономия.

## Где продолжать

### DATA-1 — Асанали, 23 сентября 2026

Ветка `asanali/data-reconciliation`: добавлена диагностическая сверка месячных продаж и динамики партнёрских ZIP по поставщику, строковому коду 1С и месяцу. `meta.reconciliation` содержит подписанные суммы расходных накладных и прочих документов, разницу с месячной формой, статусы отсутствующих источников, пометку неполного месяца и число нераспознанных строк. Товары только из динамики сохраняются в отчёте. При повторном импорте отчёт поставщика заменяется; отчёты других поставщиков сохраняются. CLI: `--reconciliation-output data/reconciliation.json`. Подробности и ограничения — в README.

Формула заказа, интерфейс и существующие маршруты API сохранены; отчёт — дополнительное поле метаданных. Не содержит номеров документов, клиентов, названий товаров и складов, но коды и количества всё равно коммерческие: отчёты хранить локально, не публиковать в Git.

Проверено: исходные 20 тестов; после изменений 29 тестов через `.venv/Scripts/python.exe -m unittest discover -s tests -v`. Новые тесты строят синтетические Excel/ZIP в памяти, проверяют знаки, пропуски, строки только в динамике, ведущие нули, допуск, разделение поставщиков, повторный импорт через HTTP и CLI-выгрузку. В браузере пройдено «Демо-сценарии → карточка DEMO-001 (250 шт.) → выбор → утверждение синтетического заказа»; CSV возвращает HTTP 200. Локальный запуск: `.venv/Scripts/python.exe server.py`, http://127.0.0.1:8765.

Реальные `Systeme electric.zip` и `IEK.zip` отсутствовали на компьютере Асанали; сопоставимость реальных продаж не проверена. Следующий шаг — получить их у команды, локально построить отчёт и уточнить причины расхождений (периметр складов/единиц, даты выгрузок и назначение прочих документов). MODEL-1 остаётся отдельной свободной задачей.

Приоритеты и независимые области работы — в `TASKS.md`. Сначала воспроизвести текущий запуск. Не начинать проект заново и не менять стек ради изменения стека. После изменений обновить тесты, документацию и этот файл. При работе с двумя ИИ явно указывать ветку, задачу и файлы, чтобы они не правили одну область одновременно.
