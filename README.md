# 7-Solutions — пополнение склада

Рабочий прототип для кейса «Автоматический расчёт заказов поставщикам для пополнения склада», ТОО «Электрокомплект». HackAlem AI, 23 сентября 2026. Команда: Мадияр и Асанали.

Приложение читает предоставленные ZIP с Excel, формирует объяснимые рекомендации для IEK и Systeme Electric, позволяет уточнить остаток и количество, утверждает заказ и выгружает CSV для Excel. Данные обрабатываются локально; внешние AI API не вызываются. Прогноз — воспроизводимая статистическая модель. Codex использован при разработке.

## Запуск

Требуется Python 3.11 или новее и openpyxl 3.1.x.

```sh
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS / Linux: source .venv/bin/activate
python -m pip install -r requirements.txt
python server.py
```

Открыть http://127.0.0.1:8765. На исходном компьютере можно запустить `run.cmd`: он использует готовый Python из среды Codex, если тот доступен. Альтернативный порт: `python server.py --port 8766`.

Код работает без сети после установки зависимости. Сервер слушает только localhost. Это локальный прототип, не многопользовательский production-сервис; не следует открывать его напрямую в интернет.

## Данные

В интерфейсе загрузить оба архива `Systeme electric.zip` и `IEK.zip`. Они читаются в памяти, без извлечения путей ZIP на диск. Лимит загрузки — 40 МБ; суммарного распакованного размера Excel — 150 МБ. Импорт ZIP обновляет соответствующего поставщика. JSON заменяет весь набор.

Также доступен импорт из командной строки:

```sh
python importer.py "Systeme electric.zip" "IEK.zip"
```

Результат хранится в `data/dataset.json`. В локальной сборке для команды данные уже загружены. Исходный архив для передачи кода и Git исключают коммерческие данные и утверждённые заказы. После клонирования импортировать данные заново либо открыть «Демо-сценарии».

Проверенные входы: 12 файлов, 3 908 уникальных пар поставщик–код 1С, 248 467 положительных строк расходных накладных. 724 позиции Systeme Electric и 3 184 позиции IEK. Это объединение справочников, поэтому не у каждого товара есть все источники.

### Особенности источников

* Основные продажи в динамике положительные. Отрицательные записи не превращаются в положительный спрос; они уже влияют на нетто-продажи месячных отчётов. Обнаружение выбросов работает по положительным накладным.
* Код 1С и артикул поставщика хранятся строками. Соединение выполняется по коду 1С в рамках поставщика; начальные нули и подчёркивания сохраняются.
* Пустые продажи в месячной форме 1С трактуются как 0. Это допущение формата. Пустые остатки остаются неизвестными.
* У Systeme Electric в отчёте товаров в пути есть свободный остаток на 22.09.2026 и поступление 24.09.2026. Колонка «Заказ» не используется как предсказание.
* У IEK доступны месячные начальные остатки, а не подтверждённый свободный остаток на 22 сентября. Для утверждения нужен ручной актуальный остаток или нормализованный импорт.
* «MOQ» у Systeme содержит кратность, у IEK — минимально разрешённую отгрузку. Минимум и кратность не подменяют друг друга. Для IEK кратность по умолчанию 1 учётная единица, пока не передано иное.
* Позиции с закупкой бухтами и учётом метрами блокируются до согласования единиц. В нормализованном JSON нужно привести все количества к одной учётной единице и установить `unit_review: false`.
* В динамике нет ID клиента. Проверка регулярности покупок одного клиента работает только при передаче обезличенного `customer_id` в нормализованном JSON.
* Месячные остатки не позволяют точно восстановить дни stockout. Такие периоды не выдумываются: компенсация применяется при наличии `stockout_days`. Демо содержит подтверждённые синтетические периоды.
* Категории в исходном отчёте Systeme присутствуют как коды без расшифровки. Множитель страхового запаса задаёт менеджер через «Политику категорий». Значение по умолчанию 1; бизнес-смысл кодов не придумывается.

## Методология

1. **Выбросы.** Строки объединяются по дате, накладной и, при наличии, клиенту. При минимум восьми накладных порог равен `max(5 × медиана, медиана + 6 × 1.4826 × MAD, 1)`. Из исключительной накладной вычитается часть выше медианы обычного заказа. Крупные покупки одного известного клиента на трёх и более отдельных датах сохраняются. Без ID клиента доступны только эвристики по накладным. Обнаружение не является доказательством разового характера покупки.
2. **Сезонность.** Каждый полный год нормализуется к своему среднемесячному уровню. Используется смесь сезонности товара (65%) и поставщика (35%). При отсутствии полного года используется сезонность поставщика. Для поставщика берутся полные 2024–2025 годы. Сезонность выручки поставщика является приближением сезонности количества; доли и цена могут меняться.
3. **Базовый спрос.** Последние шесть полных месяцев очищаются от избыточной части накладных; количества переводятся в дневной спрос и делятся на сезонный индекс. Среднее даёт базовый дневной уровень. Текущий неполный месяц не входит в обучение.
4. **Stockout.** При известных днях отсутствия спрос восстанавливается из скорости продаж в дни наличия. Для полностью пустого месяца используется устойчивый сезонный базовый уровень. Добавленный спрос явно показан в карточке. Без этих данных компенсация не применяется, что отмечено в интерфейсе.
5. **Рост.** При трёх и более сопоставимых месяцах вычисляется медиана отношения к прошлому году. Текущий уровень уже учтён в базе, поэтому исторический рост экстраполируется только на горизонт планирования. Если передан отдельный прогноз прироста (в исходном отчёте Systeme — «Кэф. Роста»), применяется он. Менеджер может задать дополнительный процент. Это разные источники, не дважды применённый один коэффициент.
6. **Горизонт.** Срок новой поставки + период между заказами. Дневной спрос суммируется по календарю с сезонностью каждого месяца горизонта. Страховой запас = текущая дневная скорость × заданные дни × множитель категории.
7. **Поставки.** Вычитаются только положительные поставки с ожидаемой датой от даты расчёта до конца горизонта. Просроченные поступления не считаются доступными автоматически. Риск дефицита рассчитывается по дням с учётом дат поступлений: поздняя большая поставка не скрывает ранний дефицит.
8. **Количество.** `max(0, прогноз + страховой запас − свободный остаток − поступления в срок)`. Положительная потребность доводится до минимума партии и округляется вверх по кратности.

По умолчанию: дата 23.09.2026, срок поставки 30 дней, период заказов 14 дней, страховой запас 14 дней. Это допущения для демо; договорные сроки не представлены. Общие параметры действуют на текущий расчёт всех поставщиков. Для разных условий можно рассчитывать и утверждать поставщиков поочерёдно.

Неизвестный остаток для предварительной оценки принимается равным 0, но утверждение блокируется. Остаток на начало месяца отмечается как предварительный. Неизвестная кратность, несогласованные единицы и история менее трёх из последних шести месяцев также блокируют утверждение.

## Нормализованный JSON

Пример доступен на странице «Источники и качество» или `GET /api/template`. Это синтетический набор; перед загрузкой заменить поля своими обезличенными данными. Пример минимальной позиции:

```json
{
  "items": [{
    "id": "IEK:SKU-001",
    "supplier": "IEK",
    "code": "SKU-001",
    "sku": "SUPPLIER-001",
    "name": "Товар",
    "unit": "шт",
    "category": "1",
    "sales": {"2026-03": 90, "2026-04": 100, "2026-05": 50, "2026-06": 110, "2026-07": 120, "2026-08": 130},
    "stock": 20,
    "stock_kind": "current",
    "stock_date": "2026-09-23",
    "stockout_days": {"2026-05": 15},
    "growth_forecast": 0.1,
    "pack": 5,
    "minimum": 10,
    "inbound": [{"eta": "2026-10-01", "quantity": 30}],
    "transactions": []
  }]
}
```

`growth_forecast` — доля прироста (0.1 = +10%), `seasonality` — необязательный массив из 12 индексов. `transactions` содержит `date` (YYYY-MM-DD), `document`, положительное `quantity`, необязательный обезличенный `customer_id`. Суммы транзакций и месячная история должны относиться к одному периметру. Нормализованный импорт не публикует данные и не отправляет их третьим сторонам.

## Утверждение и экспорт

Открыть карточку товара → при необходимости подтвердить свободный остаток и пересчитать → изменить количество с соблюдением партии → «Выбрать в заказ» → «Утвердить и выгрузить» → ввести ответственного. На сервере повторно проверяются ограничения. Изменение параметров сбрасывает выбранные позиции; импорт инвалидирует предыдущие расчёты.

Снимок утверждения хранится в `data/order-<id>.json`, включая параметры, рекомендации и ручные количества. CSV — UTF-8 с BOM, разделитель `;`, строки сгруппированы по поставщикам. Обозначение `demo`/`real` включено в экспорт. Ячейки с формульными префиксами экранируются. Автоматической отправки поставщикам нет. Совместимость с конкретной обработкой импорта в 1С ещё нужно согласовать с владельцем кейса.

## Проверка

```sh
python -m unittest discover -s tests -v
```

Тесты проверяют устойчивость к искусственному всплеску, повторные покупки клиента, сезонность, компенсацию stockout, рост, категории, партии, сроки поступления, ручной остаток, блокировки и полный цикл API «расчёт → утверждение → CSV». Это функциональная проверка, а не доказательство экономии или точности на будущих продажах. Ретроспективная оценка без утечки будущего и пилот с менеджером остаются следующим этапом.
