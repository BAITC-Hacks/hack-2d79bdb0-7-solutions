## Архитектура

- Локальный запуск не изменён: `python server.py`, SQLite, http://127.0.0.1:8765.
- Облачный запуск: Render Free → Gunicorn → `wsgi.create_app()` → те же маршруты и расчётный движок → PostgreSQL Neon Free. Стандартный HTTP-сервер не выставляется в интернет.
- `APP_ENV=cloud`, `DATABASE_URL` и точный HTTPS-origin обязательны. Render автоматически предоставляет `RENDER_EXTERNAL_HOSTNAME`; для собственного домена задать `APP_ORIGIN=https://example.com`. SQLite fallback в облаке запрещён.
- Публичная регистрация в облаке закрыта. Набор общий для допущенной команды; каждый участник может импортировать данные. Заказы и расчёты доступны только владельцу. Это одно закрытое командное пространство, не многоклиентский SaaS.
- Пароли сохраняются как PBKDF2-хеши. Cookie: HttpOnly, SameSite=Strict, Secure в облаке. CSRF, Host и Origin проверяются. PostgreSQL TLS проверяет сертификат и имя сервера через certifi.
- Вход в Render/GitHub/Neon и аккаунт приложения — разные учётные записи. Доступ к исходникам не даёт доступа к рабочей базе.

При переходе команды на main изменить ветку в настройках сервиса и YAML одновременно. Не настраивать фоновый автокоммит или автоматическое слияние PR.

3. Ввести `DATABASE_URL` из нужного проекта Neon в секреты Render. Никогда не помещать URL в исходники, PR, чат или браузерный JS. Подключение стороннего сервиса к приватному коду/базе согласовать с владельцем.
4. Перенести данные отдельно, затем выполнить первый deploy и проверить публичный HTTPS URL: `/healthz`, закрытую регистрацию, вход, расчёт, утверждение, CSV и сохранность после нового deploy.
5. Убедиться по журналу Render, что следующий коммит действительно вызвал успешную сборку и обновление сайта. До этой проверки автодеплой считается только подготовленным.

GitHub Pages не исполняет Python и PostgreSQL. Бесплатный Render засыпает при простое; первый запрос может ждать около минуты. Его файловая система временная, поэтому `data/` на Render не используется как рабочее хранилище. Neon Free имеет квоты (на момент проверки 0.5 GB/проект, 100 CU-hours/месяц, 5 GB исходящего трафика/месяц); контролировать расход и не включать платный план автоматически. База закрыта паролем и TLS, но это не private-network hosting.

## Перенос базы

Инструмент `cloud_admin.py` запускается локально, не является HTTP API. Установить `requirements-cloud.txt`. Использовать существующий URL PostgreSQL через переменную окружения `DATABASE_URL` или игнорируемый файл `data/neon-url.secret` с одной строкой URL. Файл не входит в архив кода и не передаётся Асанали. Для сервера используется переменная окружения, не локальный файл.

```sh
python -m pip install -r requirements-cloud.txt
python cloud_admin.py --url-file data/neon-url.secret migrate --source data/app.sqlite3
```

Перед выполнением прекратить изменения локальных данных: миграция — разовый снимок, не двусторонняя синхронизация. Команда создаёт согласованную копию SQLite и копии старых JSON в `data/backups/<UTC>/`, проверяет целостность, переносит пользователей, набор и заказы только в **пустую** PostgreSQL. В одной транзакции сравнивает все перенесённые поля; ошибка откатывает перенос. Повторный запуск на непустую базу прекращается без перезаписи. Сессии и временные расчёты не переносятся — войти заново. Исходная база не удаляется и не меняется.

На компьютере Мадияра при подготовке найдено 3 908 товаров, 1 аккаунт, 0 новых SQLite-заказов и 2 старых `order-*.json`. Пользователь явно выбрал **сохранить старые заказы только в закрытом архиве до уточнения владельца**. При будущем переносе они попадут в `documents.kind=legacy_order`, без владельца и без показа в личной истории. Не назначать их Мадияру автоматически.

Права новых членов команды добавляются владельцем базы через `python cloud_admin.py create-user` (DATABASE_URL в окружении); пароль вводится скрыто через getpass. Нет сброса пароля письмом, приглашений или ролей. После включения общего сервера использовать его как единственный источник актуальных данных; локальные SQLite между компьютерами не синхронизируются.

## Проверки и ограничения

- 48 локальных тестов маршрутов, расчёта, импорта, входа и резервного копирования проходят.
- Дополнительный PostgreSQL-тест `tests/test_postgres.py` прошёл на настоящем Neon в отдельной временной схеме. Проверены перенос, повторный запуск без перезаписи, пароль после переноса, sequence ID, сессии, upsert и запрет чужого заказа. Временная схема удалена; рабочая `public` не заполнялась.
- Для повторения интеграционного теста задать `TEST_DATABASE_URL` и запустить `python -m unittest discover -s tests -p test_postgres.py -v`. Тест создаёт и удаляет только собственную схему `seven_test_<uuid>`. Без переменной тест пропускается.
- Сборка Render запускает тесты без облачных переменных, чтобы они никогда не работали с рабочей БД.
- Публичный сервер, реальные мигрированные данные, автодеплой и нагрузка на свободном тарифе ещё не проверены. Исходный JSON-импорт DATA-2 и ограничение числа запросов по IP остаются задачами перед более широким доступом.
